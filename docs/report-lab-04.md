## Мета роботи

На локальному навчальному стенді SecureLab (baseline 2-A) відтворити IDOR/BOLA, усунути доступ до чужого ресурсу на сервері та підтвердити виправлення перевірками для ролей `Reporter` і `Analyst`.

## Етап 4. Виправлення серверної авторизації

### Крок 1. Захист групи маршрутів `/api/incidents`

Групу `/api/incidents` захищено через `RequireAuthorization()`.

**Докази:** рисунки 20–21 у Word-звіті.

### Крок 2. Перегляд деталей: id користувача з principal

Ідентифікатор користувача береться з `HttpContext.User` (`ClaimTypes.NameIdentifier`). Власник або `Analyst` отримує доступ, інший користувач — **403**.

**Доказ:** рисунок 22 у Word-звіті.

### Крок 3. Сценарії A-02, A-03 і A-03R

Перевірено:
- **A-02** — Alice читає власний інцидент (**200**)
- **A-03** — Alice не читає інцидент Bob (**403**)
- **A-03R** — Morgan читає інцидент Alice (**200**)

**Докази:** рисунки 23–25 у Word-звіті.

### Крок 4. Сценарій A-05: список інцидентів

- Alice бачить лише власні інциденти
- Morgan бачить інциденти для аналізу

**Докази:** рисунки 26–28 у Word-звіті.

### Крок 5. Перевірка власника в `UpdateIncidentAsync`

Оновлення дозволено лише власнику з роллю `Reporter`.

**Доказ:** рисунок 29 у Word-звіті.

### Крок 6. Обмеження списку у запиті до БД

У `IncidentQueries.GetListAsync` додано фільтрацію за власником або роллю `Analyst`.

### Крок 7. Сценарій A-04: спроба змінити інцидент Bob

## Основний security finding: до → причина → виправлення → після

1. **Стан до.** Alice могла змінити чужий інцидент Bob.
2. **Причина.** Сервер шукав інцидент лише за ID без перевірки права доступу.
3. **Виправлення.** Реалізовано `CanAccessIncident`, перевірку principal, фільтрацію списку та захист DTO.
4. **Стан після.** Alice отримує **403**, чужі дані не змінюються.
5. **Тестування.** Усі потрібні сценарії перевірено, **28/28 тестів успішні**.
6. **Залишкові ризики.** Захист від CSRF і сценарій A-11 виходять за межі цього рівня.
