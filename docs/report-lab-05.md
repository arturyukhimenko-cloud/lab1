## 2. Змінений маршрут

У лабораторній роботі досліджено маршрут передавання та відображення даних інциденту від браузера до PostgreSQL і назад.

Основний маршрут:

1. Користувач вводить опис інциденту через браузерний клієнт SecureLab.
2. Браузер надсилає JSON-запит до API через `POST /api/incidents`.
3. Сервер перевіряє вхідні дані та зберігає їх у PostgreSQL.
4. Під час відкриття інциденту браузер надсилає `GET /api/incidents/{id}`.
5. Сервер отримує дані з бази та повертає JSON із полем `description` і коментарями.
6. Файл `browser-lab.js` отримує відповідь та відображає дані у DOM.

Ключові файли:

- `src/SecureLab.Api/Client/browser-lab.html` — сторінка перегляду інциденту.
- `src/SecureLab.Api/Client/browser-lab.js` — отримання та відображення даних.
- `src/SecureLab.Api/Presentation/Endpoints/IncidentEndpoints.cs` — API-маршрути інцидентів.
- `src/SecureLab.Api/Application/Incidents/IncidentQueries.cs` — отримання даних інциденту.
- `src/SecureLab.Api/Data/SecureLabDbContext.cs` — взаємодія з PostgreSQL через Entity Framework Core.
- `src/SecureLab.Api/Program.cs` — налаштування CORS, CSP та HTTP middleware.

До виправлення дані користувача відображалися через `innerHTML`, через що браузер міг інтерпретувати їх як HTML.

Після виправлення використовується спільна функція:

```javascript
function renderText(element, text) {
    element.textContent = text ?? "";
}
```

Це дозволяє відображати збережені значення як звичайний текст без створення HTML-елементів із недовірених даних.

## 3. Виконані зміни

### 3.1. Усунення stored XSS

У початковому стані було виявлено два небезпечні місця відображення даних:

- `Incident.Description`;
- `IncidentComment.Text`.

Причиною була передача користувацького тексту до властивості `innerHTML`.

Для виправлення створено спільну функцію `renderText()`, яка використовує `textContent`.

У файлі `browser-lab.js` замінено небезпечне відображення опису інциденту та текстів коментарів.

Після виправлення HTML-подібні значення залишаються текстом, а браузер не створює відповідні HTML-елементи.

### 3.2. Налаштування CORS

У `Program.cs` додано навчальну політику `Lab05BrowserProbe`, яка працює лише в середовищі `Development`.

Основні параметри:

- Дозволений origin: `http://localhost:4173`.
- Недозволений origin: `http://localhost:4174`.
- Дозволений метод: `GET`.
- Дозволений заголовок: `X-Lab-Cors-Probe`.
- Підтримка credentials: `.AllowCredentials()`.

Middleware CORS розміщено після `UseRouting()` та перед автентифікацією й авторизацією.

Це дозволяє браузеру правильно обробляти CORS-заголовки, зокрема для відповідей `401 Unauthorized`.

У Production навчальна CORS policy не застосовується.

### 3.3. Налаштування CSP

У `Program.cs` додано Content Security Policy у режимі enforcement.

Основні директиви:

- `default-src 'self'`
- `script-src 'self'`
- `style-src 'self'`
- `connect-src 'self'`
- `img-src 'self' data:`
- `frame-ancestors 'none'`
- `object-src 'none'`
- `base-uri 'self'`

CSP обмежує джерела ресурсів, дозволяє необхідні локальні JavaScript- і CSS-файли та забороняє вбудовування основних сторінок у сторонні iframe.

Для стороннього інтерфейсу документації `/scalar` передбачено виняток лише в `Development`.

### 3.4. Захисні HTTP-заголовки

Перевірено:

- `X-Content-Type-Options: nosniff` — зменшує ризик неправильного визначення MIME-типу браузером.
- `Referrer-Policy: no-referrer` — обмежує передавання інформації про попередню адресу сторінки.
- `frame-ancestors 'none'` — зменшує ризик clickjacking.

Наявність заголовків підтверджено через Chrome DevTools → Network → Response Headers.

## 5. Security-сценарій

### Гіпотеза

Якщо користувач зберігає HTML-подібний текст у полі інциденту, а браузер відображає його через `innerHTML`, це може призвести до stored XSS.

### Стан до виправлення

У vulnerable commit `d491dc6` обидва поля використовували небезпечне відображення через `innerHTML`.

Для перевірки застосовано локальний навчальний marker із файла `resources/lab05-marker.txt`.

Marker виконував тільки контрольовану DOM-дію всередині локального стенда SecureLab.

Під час демонстрації отримано результат `executed`.

### Першопричина

Причина вразливості — передавання недовірених значень `description` та `comments[].text` до HTML parser через `innerHTML`.

Серверне зберігання даних у БД не робить користувацький текст безпечним для HTML-інтерпретації.

### Виправлення

Використано `textContent` замість `innerHTML`.

Значення зберігається та повертається через API як текст, а безпечна DOM-функція не дозволяє браузеру інтерпретувати його як HTML.

### Повторна перевірка

Після виправлення:

- XSS-marker більше не виконується.
- `Incident.Description` відображає HTML-подібний текст без створення HTML-елементів.
- `IncidentComment.Text` також відображається як текст.
- Для повторно створеного тестового інциденту підтверджено збіг значення JSON та DOM.
- Після ввімкнення CSP регресійні перевірки залишилися успішними.

### Позитивна регресія

Перевірено звичайний текст із лапками, символами порівняння, Unicode та HTML-подібними фрагментами.

Після виправлення ці значення не повинні втрачатися або перетворюватися на HTML.

### Короткий review XSS, CORS, CSRF та авторизації

**XSS** — небезпека виконання недовіреного коду в браузері. Основний захист у нашому сценарії — правильне відображення тексту через `textContent`.

**CORS** — механізм браузера, який контролює читання cross-origin відповідей. Він не забороняє всі HTTP-запити до API та не замінює серверну авторизацію.

**CSRF** — ризик небажаних запитів від імені користувача з активною сесією. CORS не є повноцінним CSRF-захистом. Для state-changing операцій потрібні окремі захисні механізми.

**Авторизація** — серверна перевірка прав доступу. Навіть дозволений CORS origin не отримує автоматично доступ до захищених даних без належної автентифікації.

### Залишковий ризик

CSP є додатковим рівнем захисту, але не замінює виправлення небезпечних DOM-операцій.

Потребують подальшої уваги інші можливі DOM-sinks, URL- та attribute-контексти, сторонні JavaScript-компоненти й CSRF-захист для операцій зміни даних.

## 6. Висновок

Під час виконання лабораторної роботи №5 було досліджено браузерні механізми безпеки вебзастосунку SecureLab.

Виявлено та усунуто stored XSS у полях `Incident.Description` і `IncidentComment.Text` шляхом заміни небезпечного `innerHTML` на безпечне відображення через `textContent`.

Також налаштовано CORS для навчального середовища, додано Content Security Policy та перевірено захисні HTTP-заголовки.

Практично підтверджено різницю між серверною відповіддю й можливістю браузерного JavaScript прочитати її, а також відмінність CORS від авторизації та CSRF-захисту.

Після всіх змін виконано повторні перевірки XSS, CORS і CSP. Автоматичні тести завершилися успішно: 28 із 28 без помилок.

Фінальний стан збережено в Git, позначено тегом `v0.5.0` і передано до гілки `main` на GitHub.

Мету лабораторної роботи досягнуто. Отримано практичні навички пошуку, відтворення та виправлення браузерних вразливостей, налаштування політик безпеки й перевірки результатів.
